# Workflow Documentation

## Purpose

Workflow documents describe repeatable work from trigger to completed output.

## Standard workflow format

| Section | Description |
|---|---|
| Trigger | Event that starts the workflow |
| Intake | Information required before work starts |
| Roles | Accountable owner and contributors |
| Steps | Ordered actions and decision points |
| Evidence | Links, notes or artifacts proving completion |
| Output | Deliverable, decision or next stage |
| Handoff | Where the next owner continues work |

## Documentation rules

- Keep the operational sequence in GitHub.
- Keep the working evidence in ClickUp and Drive.
- Use decision logs for material changes to process design.
- Review high-volume workflows quarterly.

## Storage and tooling boundaries
- GitHub stores this workflow, governance, SOP and system documentation.
- Google Drive stores live client folders, signed documents, deliverables and working files.
- ClickUp stores execution, pipeline stages, owners, due dates and task evidence.
- Gmail stores correspondence and approved communication templates.

## Repository hygiene
- Do not commit signed contracts, confidential client files, exports, duplicate folders or ad hoc drafts.
- Use clear version history through commits and pull requests instead of `final_final` filenames.
- Keep client-specific details in the appropriate live workspace, not in this repository.
