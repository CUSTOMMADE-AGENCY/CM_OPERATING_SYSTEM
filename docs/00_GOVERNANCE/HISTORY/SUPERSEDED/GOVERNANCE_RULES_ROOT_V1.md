# Governance Rules

## Core rule

One repository equals one source of truth for CM operating documentation. GitHub holds the standards; execution systems hold execution records.

## Non-negotiables

- Do not add content from unrelated operating systems or brands.
- Do not store signed contracts in this repository.
- Do not store confidential client files in this repository.
- Do not store live data-room material, private buyer files, finance files, or legal execution copies in this repository.
- Do not create duplicate documents for the same standard.
- Do not use informal names such as `final`, `final_final`, `new`, `copy`, or `latest`.

## Required documentation

- All workflows require workflow documentation before they are considered operational.
- All implemented systems require as-built documentation after setup or material change.
- Every document must be versioned when released for use.
- Changes to workflows must update the relevant README or process register when the change affects how the lane operates.

## Versioning standard

Use formal semantic-style document versions:

- `V1.0` for first approved release.
- `V1.1` for minor content updates that do not change the operating model.
- `V2.0` for major structural changes, ownership changes, or process redesign.

## Naming standard

- Use uppercase file names with underscores for operating documents.
- Use clear business language.
- Include the lane or function when ambiguity is possible.
- Keep names stable so links and references remain reliable.

## Archive standard

- Archive old versions in the approved archive location.
- Keep the active version clearly identifiable.
- Do not leave obsolete documents beside active documents without archive status.
- Record material changes in the document history section when applicable.
